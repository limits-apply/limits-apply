The local half

Two aliases: build and plan.

The site explains the verdict. Gate executes it — a TypeScript CLI that generates a local LiteLLM configuration, points OpenCode at it, and keeps both aliases resolving to whatever currently wins.

Neither half recreates the other's ranking. Gate consumes the same verdict the page renders.

Install

Four files, no secrets.

Gate keeps everything it owns under a single root directory. Three of those files are outputs; one of them is yours.

profile.json
Your local overlay. The only file you edit.
verdict.json
The verdict currently active on this machine.
litellm.yaml
Generated proxy configuration — an output, never a setting.
audit.jsonl
One line per transition: activation, no-op, failure, rollback.

Provider secrets never enter any of these files. Gate records credential names and whether they are available; the values stay in your environment or secret store, and nothing published here — this page included — can read them.

This page is the narrative: why two aliases, the audit model, the recovery argument. The install steps, the full command reference and a runnable quickstart live in the docs.

Stable aliases

Two names that outlive the models behind them.

build and plan are stable, periodically recomputed names. What each one resolves to is an ordered chain of access paths rather than a single one — tried best first, with a path that has just refused a request skipped until it recovers. When the verdict changes, the names keep their names and the chains change underneath, so nothing in your editor configuration has to move either way.

One access path per failure domain. Two paths onto the same account share a ceiling, so the second is not a route out of the first — the ranking keeps the better one and drops the other.

Four fields in profile.json overlay that workload, and none of them are uploaded:

What you are actually willing to spend each month.

Where you are, which decides what is available to you at all.

An overlaid workload carries its own identity, global-v1+local, so a personalised verdict is never mistaken for the published one — in the audit log or anywhere else.

Update status

Three outcomes, all of them logged.

noop
The new verdict is identical to the one already active and the configuration it generates already matches what is on disk. Nothing is written — and a configuration that has drifted from either is rewritten rather than skipped.
activated
A candidate passed every check and replaced the previous configuration.
failed
A candidate was rejected. The active configuration is untouched.

A candidate has to clear three checks before it can become active:

  1. both build and plan aliases are present;
  2. the master key setting is LITELLM_MASTER_KEY;
  3. the proxy binds to 127.0.0.1.

A live ping to each alias runs after activation, not before it — informational today, not a gate. A rate-limited alias counts as a pass: an HTTP 429 proves the route reached a real provider, which is the only thing that check is asking. A 200 that never says pong does not.

Recovery

Nothing is replaced until its replacement works.

Every file Gate replaces is written to a temporary name and renamed into place, so an interrupted update leaves the previous configuration whole rather than half-written. audit.jsonl is appended to, not replaced, so this guarantee doesn't cover it.

If a candidate fails validation, the previous configuration stays active and the attempt is logged with the reason it was rejected. A rollback path exists for a configuration that was already swapped in and later proves bad, but nothing calls it yet — that's still ahead, tracked on the roadmap.

Generated files are outputs, not settings. To change what Gate does, edit profile.json and update — not litellm.yaml, and not the OpenCode fields Gate owns, both of which are rewritten on the next activation.

Closed windows

Gate never counts what you have left.

It records only that a window was observed closed, and the time it was said to reopen — and it says which of the two it was told and which it inferred. A count of what remains would need a published ceiling, and dividing your usage by a published ceiling is exactly the inference this project refuses to make.

Two timescales, two mechanisms. A burst refusal is LiteLLM's problem: the path it came from cools for seconds and the chain moves on, with no involvement from Gate at all. A flat-rate window closing for hours is Gate's: the failure domain is recorded in quota.jsonl and the next update rejects every candidate on it until the timestamp passes. That rejection removes the domain from both chains at once, which per-deployment cooling cannot do.

What a record says
domain
The failure domain, not a plan or a model
resetsAt
When the window was said to reopen
rung
observed read from the refusal · derived inferred from a window length
Where it comes from

A refusal you record yourself, or one read out of OpenCode's own message records. A post-activation ping cannot supply one: a refusal at the alias means every path behind it is cooling, which names no domain.

Audit

Every transition, one line each.

audit.jsonl is append-only: one JSON object per event, in order, readable without any tooling.

event
update · activate · rollback · noop · failure
at
When the transition happened.
oldVerdict / newVerdict
Verdict identifiers either side of it.
profileHash
A hash of the overlaid profile that produced it, locally observed quota state included — comparable across entries, and non-secret.
reason
Present on a failure or a rollback: what rejected the candidate.

Credential names may appear in a profile; credential values appear nowhere, in the audit log or in anything Gate uploads — which is nothing.
