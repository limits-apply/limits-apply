Harnesses

One harness writes itself. Others were wired by hand. The rest are honest about not yet.

build and plan resolve behind a loopback LiteLLM proxy, so any OpenAI-compatible client can use them — but Gate only generates a client's own config file for one harness today. This page says which, and what it would take for the rest.

Status

One mark, and it is not the provenance ladder.

A card carries Verified when Gate writes this configuration itself, and a test compares the published snippet to the code that writes it. Nothing else on this page carries a mark: a configuration below it was pasted in by hand on the date its card names, and a card with no configuration has none to publish. The mark is deliberately not the measured · observed · derived · chained · modelled ladder the benchmark tables use, which is about the strength of a figure, not whether Gate can talk to a tool.

Recommended

One writes itself. The others were wired by hand, on a dated afternoon.

Gate writes only OpenCode's config file itself; that snippet is generated from mergeOpencodeConfig, the same function gate.html describes. Pi, Codex and Claude Code were configured by hand and answered on the date each card carries — Gate does not write them, and nothing catches them drifting. Pi answered on both aliases; Codex and Claude Code answered on build only, because that day's plan model was served in the chat-completions shape alone.

Compatible

Reachable through the proxy, unconfigured by Gate.

Each of these speaks an OpenAI-compatible surface, so the proxy is reachable from any of them by hand — the openai-compatible row describes it. Gate writes none of their config files, and no configuration here has been run, so none is published. What it would take for each is on the roadmap.
